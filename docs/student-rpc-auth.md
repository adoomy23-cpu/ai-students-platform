# إصلاح هوية الطالب عبر RPC — حالة التنفيذ والحدود

الفرع: `fix/alfikr-student-rpc-auth`، من أحدث فرع إصلاح مفحوص
`fix/alfikr-student-profile-resolution` عند Commit GitHub
`52fcfc487d09cb182ed899d54a92cbdb2f7a47c7`.

قورنت نسخة الحسابات `20c0c6c` بالإصلاح السابق؛ الفرق 10 ملفات تتضمن توحيد
التوجيه وتفسير أخطاء التحقق وتشخيص الربط. شجرة الملفات المحلية تطابق
الإصلاح السابق، وكل هذه التحسينات محفوظة في الفرع الجديد.

## الأدلة المتاحة

أكد صاحب المشروع في نتائج فحص Supabase أن students محمي بـRLS للمدير،
وأن `public.get_my_student_profile()` بلا معاملات، SECURITY DEFINER،
ومسموح لـauthenticated بتنفيذها، وأن search_path هو public، وأن تعريفها
يحتوي `auth.uid()` و`s.user_id = auth.uid()`.

هذه نتائج مؤكدة من صاحب المشروع؛ **لم ننفذ اتصالًا حيًا مستقلًا للتحقق منها**.
لا إعدادات اتصال متاحة هنا، ولم نعثر في المستودع على تعريف الدالة الكامل
أو نوع الإرجاع الفعلي. احتواء الدالة على شرط الهوية وحده لا يثبت جميع
فروع التنفيذ أو أن النتيجة الفارغة تعني عدم وجود ملف؛ نحتاج كامل التعريف.

## التغييرات المنفذة

- `inspectOwnStudent` يستدعي `client.rpc("get_my_student_profile")` بلا
  معاملات بدل SELECT من students. يستعمله كل من API حالة الجلسة وبوابة
  الاختبارات والتحديات والرفع؛ بنفس JWT الطالب والمفتاح العام الحالي.
  لا تمرير user_id من المتصفح ولا رجوع إلى قراءة الجدول عند فشل RPC.
- التوجيه الموحد السابق محفوظ: المعتمد إلى الاختبارات، والمعلّق والموقوف
  والمرفوض إلى صفحة الحالة، وفشل التحقق إلى رسالة وإعادة محاولة. تغيير
  الحساب والخروج وانتهاء الجلسة يبطل الصلاحية السابقة والمسودات المرتبطة.
- فحص النتيجة وقت التشغيل يرفض أكثر من سجل أو مستخدمًا آخر أو حالة غير
  معروفة. يخرج للواجهة بيانات العرض المسموح بها فقط، دون البريد وuser_id
  والحقول الإضافية. لا يقرأ دليل الطلاب ولا يمنح إدارة من بيانات الملف.
- قراءة الصف والفصل الاختيارية لا تلغي اعتمادًا ثبت من الملف إذا فشلت؛
  المصدر الحقيقي لعرض الموقع الدراسي من RPC يحتاج مطابقة حقوله الفعلية.
- بوابة تحميل الاختبار تُسقط حقول RPC الإضافية وتعيد فقط quiz
  (id/title/description/time_limit_minutes)، والأسئلة
  (id/question_text/points/image_url)، والخيارات (id/option_text).
  تُحجب correct_option_id/is_correct/answer_key والشروح والمحاولات والبيانات
  الإضافية، ولا تعاد نتيجة خام عند فشل المطابقة. نتيجة الإرسال score
  وtotal_points فقط. التصحيح الحقيقي يظل في RPC السابقة دون تغييره.
- `/q` كان يحتوي الإجابات الصحيحة وتصحيحها داخل ملف العميل. انتقلت أسئلته
  الحالية والتصحيح للخادم خلف نفس تحقق الطالب المعتمد، مع الحفاظ على
  الأسئلة وتصميمها والإعادة وعدم حفظ نتائج هذا الاختبار التجريبي في DB.
  أُصلح احتساب السؤال الأخير مرتين (كان يمكن أن تظهر 4/3؛ الآن الحد 3/3).
  لا مفاتيح إجابة في استجابة التحميل أو ملف صفحة العميل. محتوى التجريبي
  موجود في المستودع أصلًا، ولذلك نقلُه للخادم ليس بنك أسئلة سرّيًا لمستودع
  عام، ولا يمنع استنتاج الأجوبة بتكرار التدريب؛ التجريبي لا يسجل نقاطًا رسمية.
- إرسال مشاركة التحدي لا يعيد صف DB خامًا. هوية الطالب ومسار الملفات
  ما زالا يُربطان خادميًا مع التحقق من الاعتماد عند كل عملية.
- لا تغيير للرئيسية أو الروبوت أو بطاقاتها أو الشعار أو CSS الهوية/RTL،
  ولا alert/confirm/prompt أصلية. مكونات التنبيه والأزرار المشتركة محفوظة.

## حدود مطابقة عقد الملف — شرط لقبول الإصلاح الحي

لم نتلق حتى الآن تعريف الدالة الكامل أو نوع استجابتها. **لا نعتبر عقدها
أو نجاح دخول الطالب الحي مثبتًا**. المحلل الحالي يفحص القيم فعليًا ولا
يجرّب أسماء بديلة أو أغلفة JSON متخيلة:

- يقبل سجلًا واحدًا أو مصفوفة من سجل واحد فقط، إذا حمل الحقول المعروفة
  من جدول/شيفرة المشروع: id وuser_id وstudent_name وclassroom_id
  وapproval_status وis_active. id عدد صحيح موجب آمن، وuser_id يطابق هوية
  auth.getUser، والاسم نص غير فارغ، والحالة معروفة وis_active Boolean.
- هذه شروط قبول وقت التشغيل، **وليست وصفًا مثبتًا لشكل استجابة الدالة**.
  إن كانت تعيد student_id بدل id أو لا تعيد user_id أو تُرجع غلافًا آخر،
  فستُرفض النتيجة بأمان. يجب ضبط المطابقة بعد قراءة التعريف؛ لا نضيف SQL
  أو حقولًا للدالة لمجرد مطابقة هذا المحلل. يمكن الاستناد لنطاق RPC بعد
  التحقق الكامل بدل فرض تغيير DB لإضافة user_id إلى الاستجابة.
- `approved` مع is_active=true فقط يدخل. approved مع false موقوف؛
  pending يبقى معلقًا حتى لو كان غير نشط. التسميات يجب مطابقتها مع enum
  أو قيود القاعدة الحية، ولا تتحول القيم المجهولة إلى اعتماد.
- null أو [] بلا خطأ لا تُعامل تلقائيًا كملف غائب حتى نثبت أن الدالة لا
  تستبعد المعلّق/الموقوف أو تسقط ملفًا بسبب INNER JOIN. تعرض نتيجة فارغة
  غير محسومة، دون توجيه إلى استكمال الملف أو إنشاء حساب بديل.
- مسار missing موجود، وخيار emptyMeansMissingVerified مخصص لحقن العقد
  في الاختبار بعد إثبات دلالة الغياب؛ **ليس مفعّلًا في الإنتاج ولا يقبله
  API من المتصفح**. يبقى استكمال غياب الملف الحقيقي غير مكتمل حتى الإثبات.

## التسجيل والاعتماد وما يحتاج مراجعة

تسجيل Supabase Auth والدخول وتأكيد البريد بواجهات SDK الحالية محفوظة.
أما `register_student` وإجراء اعتماد المعلم فلا تزال تعريفاتهما غير متاحة؛
إرسال الملف والاعتماد مغلقان مع رسالة واضحة، ولا INSERT/UPDATE احتياطي
ولا اعتماد صوري. عرض الطلبات متاح فقط عبر بوابة is_admin الحالية.

جهزنا `docs/security/inspect-student-rpc-contract.sql`: SELECT واحد للكتالوج
يعيد التعريف والتوقيع ونوع الإرجاع وأسماء المعاملات/حقول RETURNS TABLE
وsearch_path وEXECUTE للدوال ذات الصلة، دون قراءة بيانات الطلاب أو استدعاء
RPC. يكمّله استعلام RLS الموجود `inspect-supabase-read-only.sql`.
لم يُنفّذ أي منهما. تُراجع التعريفات محليًا قبل مشاركة نص قد يحتوي أسرارًا
مكتوبة في دالة قديمة.

يلزم للتحقق النهائي:

1. تعريف get_my_student_profile كاملًا: الحقول والأنواع وشكل الإرجاع
   ودلالة الغياب وتقييد جميع المسارات بـauth.uid، دون فرع يكشف طلابًا آخرين.
2. تعريف register_student وإجراء الاعتماد القائم وصلاحياتهما: منع التكرار
   وانتحال user_id واعتماد الطالب لنفسه. لا نعتبر التفعيل الإداري اعتمادًا.
3. تعريف دوال الاختبارات وقيود الوقت والمحاولات ومنع تسريب التصحيح المباشر
   عبر Supabase REST/RPC. ترشيح API لا يكفي لمنع استدعاء RPC عامة مباشرة.
4. RLS وStorage لمنع الحساب الموقوف أو الطالب الآخر من الكتابة مباشرة،
   وصلاحية is_admin الحقيقية. لم تتغير السياسات ولم تثبت حمايتها الحية هنا.

**لا نحتاج تعديل RLS لإعادة SELECT المباشر.** الحل يستخدم الدالة القائمة.
لا ملف SQL تعديل/حذف/إنشاء أو تغيير بيانات في هذا الفرع. إذا كشف الفحص
حاجة فعلية لتعديل DB، يُجهز الفرق المحدد منفصلًا وينتظر موافقة صريحة.
