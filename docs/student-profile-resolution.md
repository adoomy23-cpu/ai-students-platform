# تشخيص عدم التعرف على الطالب المعتمد

المصدر المفحوص: `feature/alfikr-student-accounts` عند Commit GitHub
`20c0c6c66b6528131041de5cd78744ffcb81be0c`، مع تطابق شجرة الملفات المحلية.
فرع الإصلاح: `fix/alfikr-student-profile-resolution`.

## المسار الفعلي والسبب المثبت في الشيفرة

1. `/student-login` يعرض `StudentAuthForm`، الذي يستعمل
   `supabase.auth.signInWithPassword`.
2. `AuthProvider` يستقبل الجلسة ويتحقق من صلاحيتها عبر
   `GET /api/account/access`، ثم `auth.getUser(token)` و`rpc("is_admin")`.
3. للطالب يُستدعى `inspectOwnStudent`، وهو **لا يستدعي
   `get_my_student_profile`**. بل يقرأ مباشرة:
   `students.select("id,user_id,student_name,classroom_id,approval_status,is_active")`
   مع `.eq("user_id", verifiedUserId).limit(2)`، باستخدام JWT المستخدم
   والمفتاح العام الحاليين؛ دون service role أو تجاوز RLS.
4. قراءة ناجحة تُعيد `[]` تنتج `profile_unavailable` والرسالة المذكورة.
   خطأ Supabase أو نتيجة غير صالحة ينتجان `verification_failed`، وليس
   `profile_unavailable`. لذا ظهور الرسالة المحددة يعني أن قراءة الجدول
   أعادت صفر صفوف، وليس أن `get_my_student_profile` فشلت أو أعادت ملفًا فارغًا.
5. كان نموذج الدخول ينفذ أيضًا تحققًا مستقلًا ويتبع أي نتيجة غير محسومة
   بتوجيه إجباري إلى `/pending-approval`. وتأكيد البريد كان يكرر هذا السلوك.
   هذان خطآن في الواجهة؛ عدم القدرة على إثبات الملف لا يثبت أنه معلّق.

## ما الذي لم يمكن إثباته حيًا؟

لا إعدادات Supabase متاحة هنا، ولا ملفات `.env`، ولا تعريفات CREATE FUNCTION
أو CREATE POLICY/مهاجرات موثّقة للدوال في المستودع. الملفات SQL الموجودة
استعلامات تشخيص للكتالوج، وليست تعريفات القاعدة. بحثنا الشيفرة وسجل Git
المحلي والمسارات والوثائق؛ لم نعثر على تعريف RPC يمكن اعتماد توقيعه ونتيجته.
لذلك لا يجوز وصف سياسات RLS أو عقد الدوال بأنها مطابقة للقاعدة الحية.

تعتمد القراءة على `students.user_id` و`approval_status` و`is_active` التي
ذكرها صاحب المشروع، وعلى `id` و`student_name` و`classroom_id` المستعملة في
الشيفرة. ما زال يلزم إثبات أنواع الحقول وتسميات الحالة الحية. الحالات
المقبولة حاليًا `approved/pending/suspended/rejected`، و`is_active` Boolean
صريح، والمعرّف عدد صحيح موجب آمن. اختلاف هذه القيم يؤدي لفشل التحقق، وليس
لرسالة الصفر صفوف موضوع الفحص. لا يُعدّل هذا الإصلاح أيًا من هذه الشروط.

الأسباب المحتملة للصفر صفوف:

- RLS يخفي الملف عن SELECT المباشر، بينما قد تكون آلية الحساب السابقة
  تستعمل RPC يُسمح لها بإعادة الملف. وجود SECURITY DEFINER لم يُثبت بعد.
- الملف القديم غير مرتبط بـ`auth.users.id` الخاص بالجلسة الحالية، أو أن
  `user_id` فارغ/مختلف. السجلات التي يضيفها المعلم في الشيفرة الحالية لا
  تضبط `user_id` ولا تعادل إنشاء حساب طالب مرتبط.
- حساب أو مشروع Supabase مختلف عن الحساب أو المشروع الذي يحتوي الملف.
- لا يوجد ملف مرتبط بالفعل؛ لا نستنتج ذلك من SELECT تحت RLS غير موثّق.

**لم نثبت أيًا من هذه الأسباب في قاعدة حية.** لا ينبغي تخفيف RLS أو
اعتبار الصف الفارغ ملفًا ناقصًا لتجاوز المشكلة.

## الإصلاحات المؤكدة المنفّذة في الواجهة فقط

- إلغاء التحقق الموازي والتوجيه الافتراضي إلى صفحة الانتظار بعد الدخول.
  أصبح التوجيه تابعًا لنتيجة الجلسة الحالية في AuthProvider وحده، عبر
  `useStudentAccountRedirect` المستخدم في الدخول وتأكيد البريد.
- توجيه الطالب المعتمد من صفحة الانتظار إلى `/quizzes` عند نجاح التحقق،
  بما في ذلك بعد زر تحديث الحالة؛ دون تكرار replace لنفس المسار.
- تحويل `profile_unavailable` في محلل الاستجابة إلى حالة تحقق `error` مع
  الاحتفاظ بسبب المشكلة، بدل تقديمها كحالة حساب محسومة.
- إزالة رابط استكمال الملف من حالة `profile_unavailable`. يظهر فقط عندما
  تكون الحالة المثبتة `missing`. كذلك لا تظهر استمارة استكمال الملف حين
  تظل حالة الجلسة غير محسومة.
- لم نُخفِ رسالة تعذر التحقق ولم نمنح اعتمادًا بديلًا. الطالب الذي لا تستطيع
  القاعدة إظهار ملفه سيظل محجوبًا حتى التحقق من السبب وإصلاح العقد الصحيح.

الهدف الكامل (المعتمد يدخل، المعلّق ينتظر، من ثبت غياب ملفه يستكمل بياناته)
ما زال يتطلب إثبات عقد الملف. حالة `missing` لا يمكن تفعيلها من SELECT
فارغ تحت RLS مجهول. إرسال طلب الاعتماد واعتماده ما زالا معطّلين كما في
الفرع الأصلي لحين مراجعة الدوال القائمة.

## التشخيص المطلوب — قراءة فقط، لم يُنفّذ

1. شغّل `docs/security/inspect-supabase-read-only.sql` داخل المشروع الصحيح:
   يعرض الأعمدة والأنواع والقيود والفهارس والتسميات وتعريفات الدوال
   وRLS وصلاحيات EXECUTE. لا يعرض صفوف الطلاب أو أسرار الاتصال.
2. بعد مراجعة الأعمدة، استخدم
   `docs/security/diagnose-student-profile-binding.sql`. ضع معرّف Auth
   للحساب المتأثر محليًا بدل `NULL::uuid` دون مشاركة المعرّف. الاستعلام
   يعيد أعداد الملفات المطابقة وحالاتها فقط، ويعرض تعريفات triggers
   الربط والتسجيل في استعلام ثانٍ. لا يعرض اسمًا أو بريدًا أو كلمة مرور
   أو JWT. SQL Editor لا يمثل صلاحيات JWT للطالب، و`auth.uid()` فيه قد
   يكون NULL؛ لا نعتبر عدّ الصفوف فيه اختبارًا ناجحًا لـRLS.
3. إذا كان عدد الملفات المرتبطة 1 والمعتمد النشط 1 بينما API يرجع صفرًا:
   راجع RLS وعقد RPC ومطابقة المشروع وهوية الجلسة. إذا كان العدد صفرًا:
   راجع آلية الربط القائمة دون إنشاء طالب أو حساب بديل. إذا تعدد الصفوف:
   راجع القيود والمعالجة قبل أي إصلاح؛ لا تحذف أو تدمج سجلات آليًا.
4. راجع تعريف `get_my_student_profile` لتحديد المعاملات وشكل النتيجة
   ودلالة الغياب ومن يحق له الاستدعاء. لا نشغّله من SQL Editor بصفة
   المالك ونعتبره اختبارًا لجلسة الطالب، ولا نفترض أنه بلا معاملات.

## ما قد يحتاج موافقة منفصلة بعد التشخيص

- إن كانت RPC القائمة صحيحة، متاحة للطالب وتعيد ملفه بأمان: توصيل القراءة
  بها وفق تعريفها الفعلي إصلاح تطبيقي لا يحتاج تعديل DB. لم ننفّذه الآن
  لأن العقد غير متاح، ولا توجد محاولة تحليل أغلفة استجابة مفترضة.
- إن كان الربط `user_id` خاطئًا: يلزم إثبات ملكية السجل والحساب أولًا، ثم
  تجهيز UPDATE محدد بسجل واحد للموافقة. لا مقترح SQL لتغيير بيانات مجهولة.
- إن كانت هناك مشكلة صلاحية/سياسة فعلية: يلزم تعديل أدنى للدالة/السياسة
  يتيح قراءة الملف الذاتي فقط ويحافظ على منع اعتماد الطالب لنفسه. تُراجع
  السياسة الحالية ويُعرض فرق SQL المحدد للموافقة قبل التنفيذ؛ لا سياسة
  عامة أو service role في المتصفح أو تجاوز أمني.
