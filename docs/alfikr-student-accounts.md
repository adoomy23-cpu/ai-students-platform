# استعادة حسابات الطلاب — حالة التنفيذ

الفرع: `feature/alfikr-student-accounts`، من النسخة المعتمدة
`feature/alfikr-navigation-mobile-v2` عند Commit GitHub
`587577ec57b0fa27bec16e680db74305aa393ad8`.

## ما نُفّذ

- صفحات `/register` و`/student-login` و`/complete-profile` و`/pending-approval`،
  ومسار عودة تأكيد البريد `/auth/confirm`؛ بالمكونات المشتركة والألوان الرسمية
  وخط المدرسة المحلي وRTL. الشعار الأصلي والرئيسية المختصرة لم يتغيرا.
- تسجيل البريد وكلمة المرور والدخول وإعادة إرسال التأكيد باستخدام واجهات
  Supabase Auth SDK المعروفة. تأكيد الرابط يعتمد اكتشاف الجلسة القياسي
  في عميل Supabase الحالي، دون تغيير طريقة جلسات المعلم أو تخزين مفاتيح جديدة.
  هذه اتصالات مبرمجة، ولم يُختبر نجاحها على المشروع الحي.
- إضافة الدخول وإنشاء الحساب للقائمة العامة، وحسابي والخروج للمستخدم المسجّل؛
  الإدارة تبقى محجوبة حتى نجاح `auth.getUser` و`is_admin()` على الخادم.
- عرض اسم الطالب وصفه وفصله من ملفه وحده، دون قراءة البريد أو دليل الطلاب.
- قراءة ملف الطالب خادميًا بعميل يحمل JWT المستخدم والمفتاح العام الحالي؛
  التصفية بـ`user_id` الذي أثبته `auth.getUser`، والتحقق من ملكية الصف وعدد
  النتائج. لا تُقبل هوية مرسلة من المتصفح.
- وظائف الطلاب محجوبة افتراضيًا. المعتمد يدخل، والمعلّق والموقوف والمرفوض
  ينتقلون إلى صفحة الحالة. الزائر يدخل من صفحة الطالب. لا تتحول أخطاء الشبكة
  إلى ادعاء غياب الملف أو طلب إنشاء جديد.
- إزالة اختيار أسماء الطلاب من صفحتي الاختبار والمشاركة النشطتين؛ بوابة
  خادمية تتحقق من الاعتماد عند تحميل الاختبار، إرساله، تحميل التحدي، رفع ملف
  وإرسال مشاركة. الخادم يربط `student_id` بالطالب نفسه.
- الحفاظ على توقيع `get_quiz_for_student({p_quiz_id})` و
  `submit_quiz_attempt({p_quiz_id,p_student_id,p_answers})` المستدل عليهما
  من الشيفرة السابقة؛ لم تُستبدلا بدوال مجهولة ولم يتغير حساب النتيجة.
- الرفع إلى `student-private` بنفس هيكل المجلد السابق و`upsert:false`، مع
  إعادة التحقق، أسماء عشوائية، وحد 10 MiB لكل ملف. الصور JPG/PNG/WEBP/GIF؛
  الملفات PDF/TXT/DOC/DOCX/PPT/PPTX/XLSX/ZIP/SB3. أنواع HTML/SVG والتنفيذية
  محجوبة احترازيًا. التحقق من النوع/الامتداد لا يغني عن فحص محتوى الملفات.
  الإخفاق بعد الرفع قد يترك ملفًا غير مرتبط؛ لم يُحذف أي ملف لعلاج ذلك.
- إخفاء وظائف الطلاب مؤقتًا أثناء إعادة فحص الجلسة دون فقد الإجابات أو
  مسودة المشاركة، باستخدام React Activity. التوقف أو تغيير الحساب أو الخروج
  يمحو أهلية الاحتفاظ بالحالة والاسم السابق فورًا.
- قسم مراجعة طلبات الحسابات في `/admin/students`، عبر بوابة الإدارة
  الحالية فقط. عمليات المعلم السابقة للإضافة والاسم والتفعيل محفوظة.
  التفعيل لا يساوي اعتماد الحساب.

## الربط الذي لم يكتمل — لا تُعتبر النسخة استعادة كاملة بعد

لا توجد متغيرات الاتصال المطلوبة أو ملفات `.env` في بيئة العمل، ولا تعريفات
SQL للدوال في المستودع. لم نتصل بقاعدة Supabase ولم نقرأ أي بيانات حقيقية.

- **إرسال طلب الاعتماد واعتماده معطّلان عمدًا.** لا نعرف معاملات ونتيجة
  `register_student` ولا الدالة/الإجراء الرسمي لاعتماد الطلب. لا توجد محاولة
  استدعاء مفترض أو INSERT/UPDATE احتياطي لملف الطالب، ولا آلية صلاحيات بديلة.
- `get_my_student_profile` و`get_my_available_quizzes` و`submit_my_quiz`
  لم تُستدعَ، لأن تعريفاتها غير متاحة. قراءة الملف الحالية تستخدم الأعمدة
  التي ذكرها صاحب المشروع (`user_id`,`approval_status`,`is_active`)، وأعمدة
  الاسم ومعرّف الفصل المستعملة بالفعل في الشيفرة. أي اختلاف يفشل مغلقًا.
- التسميات المقبولة حاليًا `approved` و`pending` و`suspended` و`rejected`؛
  يجب مطابقتها مع القيود/enum الفعلي. المعتمد يتطلب `is_active === true`؛
  المعلّق لا يُصنّف موقوفًا لمجرد أن `is_active` يساوي false. القيم المجهولة
  لا تمنح دخولًا. الاسم ومعرّفات الجداول يجب التحقق من توافقها أيضًا.
- **غياب صف في SELECT تحت RLS غير موثّق ليس دليلًا على غياب الملف.**
  يظهر `profile_unavailable` دون توجيه تلقائي إلى استكمال البيانات.
  مسار `missing` جاهز، لكنه غير مفعّل بنتيجة فارغة في الإنتاج حتى التحقق
  من رؤية الطالب لملفه في جميع الحالات أو اعتماد RPC يثبت الغياب صراحة.
  الخيار `selfVisibilityVerified` في وظيفة القراءة حقن اختباري، وليس قيمة
  يقبلها API من المتصفح أو علامة اعتماد يفعّلها الطالب.
- فشل قراءة اسم الصف/الفصل لا يلغي اعتمادًا تم إثباته ولا يعيد الطالب
  إلى استكمال الملف. يظهر الاسم الدراسي غير المتاح دون اختلاق بيانات.
- حواجز الواجهة ليست إثباتًا كافيًا لحماية Supabase مباشرة. بوابات التطبيق
  تتحقق من السلطة عند كل عملية، لكن حماية REST/RPC/Storage المباشرة تبقى
  **مهمة أمنية غير مكتملة** حتى مراجعة RLS وEXECUTE والسياسات الحية.

## مراجعة Supabase المطلوبة — منفصلة، دون تنفيذ تعديل

استعلام القراءة فقط في `docs/security/inspect-supabase-read-only.sql` يجمع
كتالوج الجداول والأعمدة والقيود والفهارس والتسميات وصلاحيات الجداول وسياسات RLS (بما فيها جداول كتالوج Storage) وتعريفات
دوال الطلاب والاعتماد وصلاحيات تنفيذها. لا يقرأ صفوف الطلاب أو auth.users.
لم يُنفّذ الاستعلام ولم يُختبر على قاعدة حية. راجع التعريفات محليًا قبل
مشاركة الناتج تحسبًا لوجود أسرار مكتوبة داخل دالة قديمة.

يلزم التحقق من:

1. التعريف الكامل وتوقيع ونتيجة `register_student` و`get_my_student_profile`
   وطريقة الاعتماد القائمة. كيف يثبت الملف الغائب؟ وكيف تُعاد بيانات الاسم
   والصف والفصل وحالة الحساب؟ وهل يمنع التسجيل التكرار وربط هوية مستخدم آخر؟
2. فهرس/قيد فريد مناسب لـ`students.user_id`، وتسميات حالة الاعتماد،
   وسلوك `is_active` للطلب المعلّق. لا يُقترح إنشاء قيد قبل فحص الموجود.
3. رؤية المستخدم لملفه الشخصي وحده، بما يشمل الطلب المعلّق والموقوف؛
   وعدم تمكينه من اعتماد نفسه أو تغيير `user_id` أو ربط نتائج بطالب آخر.
4. `is_admin()` باستخدام هوية JWT الحقيقية، وصلاحيات تنفيذ دوال الطلاب
   والإدارة، وSECURITY DEFINER وsearch_path. لا تعتمد صلاحية المعلم على
   user_metadata أو البريد. فحص `get_student_directory` ضروري لأنه كان
   مستعملًا سابقًا، حتى بعد إزالة استدعائه من الواجهة النشطة.
5. RLS على محاولات الاختبارات والمشاركات، وصلاحيات bucket `student-private`:
   لا وصول عام، ولا كتابة خارج مسار طالب معتمد، ولا تجاوز عبر REST مباشرة.
6. إعدادات Supabase Auth: تأكيد البريد، Site URL، السماح بعنوان العودة
   الصحيح `/auth/confirm` لكل بيئة، وقالب البريد المتوافق مع التدفق الحالي.
   لا تغيّر هذه الإعدادات دون مراجعة منفصلة.

لا يوجد SQL لتعديل/إنشاء/حذف في هذه المرحلة. بعد قراءة التعريفات تُوصل
واجهة التسجيل والاعتماد بالعقد الموجود، وتُقترح أي حاجة SQL فعلية للموافقة.

## التحقق

- `npm test`: 180 اختبارًا ناجحًا (بيانات اصطناعية، دون اتصالات Supabase).
  تشمل ملكية الملف، التوجيه، خطأ الشبكة مقابل الغياب، الطلبات المعلّقة
  والموقوفة، منع تزوير student_id ومسار الملفات، حماية الإدارة، دورة الجلسة
  والمحافظة على المسودات، ومنع تنفيذ تسجيل مفترض.
- فحص تحليل 77 وحدة مصدر مع imports وJSX، و147 سيناريو بنيوي للمسارات:
  نجح باستخدام بدائل React/Next وبيانات اصطناعية. **ليس بديلًا لـESLint
  أو build أو معاينة بمتصفح**.
- `npm run lint`: تعذّر التنفيذ، `eslint: not found`.
- `npm run build`: تعذّر التنفيذ، `next: not found`.
- محاولة `npm ping` بحد 15 ثانية: فشل فوري `connect EPERM` إلى الوكيل؛
  لم نبدأ تثبيتًا معلقًا أو نكرر المحاولة. الاعتمادات المحلية غير مكتملة.
- Chromium: محاولة معاينة محدودة الزمن تعذرت بسبب قيود البيئة؛ لا ندّعي
  نجاح المعاينة على الجوال أو الكمبيوتر. CSS الحساب Mobile First، ولم
  تُغيّر CSS الرئيسية.
- لا إعداد TypeScript مستقلًا في المشروع؛ التطبيق JavaScript/JSX.
- اختبار التسجيل الحقيقي، تأكيد البريد، الاعتماد، الطالب المعتمد/الموقوف،
  RPC، RLS وStorage الحي مطلوب داخل Codespaces بعد توفير إعدادات المشروع
  الآمنة والتحقق من العقود، بحسابات اختبار، دون استخدام بيانات الطلاب.
